# Phase 1：需求与业务澄清（产出 01-requirements.md）

> 目标：把模糊想法变成可设计、可验收的需求。本阶段结束前不写任何实现代码。

## 1. 先定任务类型（三选一，向用户说出你的判断）

- **Spike 可行性试探**：用户问“能不能做 / 这样行不行”，产出是答案而不是保留的代码。给出试探计划、获同意后最小代价验证，结论以建议形式交付。
- **Bounded 小改动**：改动落在仓库里已存在的流程上（单接口、单组件、配置项）。问关键问题后在对话里给短设计，用户点头即可，不写长文档。
- **Architectural 架构级**：新项目、新子系统、会改变别人依赖的接口/结构。走完整流程，产出书面需求与设计。
- 拿不准就选更重的；中途发现隐藏复杂度，立即停机升级路径。

## 2. 业务拷问（一次只问一个问题）

按顺序提问，每题给 2-3 个建议选项 + “自己描述”。不要一次把问题全抛给用户。

1. **问题与用户**：这个功能解决谁的什么痛点？用户现在没有它时是怎么办的（现有替代方案是什么）？
2. **成功画面**：做成之后，用户的操作/体验具体变成什么样？
3. **验收标准**：哪些条件满足才算“done”？写成可勾选的条目，每条都能被测试验证。
4. **范围边界**：明确**不做**什么——这比做什么更重要，防止功能蔓延。
5. **技术约束**：现有接口约定、指定数据库/框架、延迟要求、复用的鉴权体系等。
6. **依赖影响**：是否依赖或影响其他功能/服务？数据是否需要迁移或兼容旧数据？
7. **技术栈确认**：把 Phase 0 自动探测到的栈给用户确认（前端框架 / 后端框架 / 数据库 / 部署目标），brownfield 以探测结果为准。

提问中的判断：如果用户的方案前提可疑（例如为不存在的用户做复杂功能、与现有产品重复），要直接提出质疑并给出替代思路，而不是照单全收。

## 3. 产出文件模板：`.fullstack-flow/01-requirements.md`

```markdown
# 需求：<功能名>

## 问题陈述
<谁，在什么场景下，遇到什么痛点；现有替代方案及其不足>

## 成功画面
<做成后的用户体验/业务结果>

## 验收标准
- [ ] <可验证条目 1>
- [ ] <可验证条目 2>

## 范围
### In Scope
- <要做的事>
### Out of Scope
- <明确不做的事及原因>

## 技术约束
<接口约定、性能/兼容要求、必须复用的系统>

## 技术栈
- 前端：<框架/UI 库>　后端：<框架>　数据库：<>　测试：<>　部署：<>

## 依赖与影响
<上下游服务、数据迁移、受影响的现有功能>

## 配置
- 复杂度：simple | medium | complex
- API 风格：rest | graphql | rpc
- 裁剪标志：--no-frontend / --no-db（如适用）
```

## 4. 闸门 A：需求确认（必须停下）

向用户展示**一页内**的摘要：要解决的问题、验收标准、范围外清单、技术栈，然后给出三个选项：

1. 批准，进入设计；
2. 需要修改（按意见修订后重新确认）；
3. 暂停（保存进度，state.json 记录停在此处）。

用户未明确选 1 之前，不进入 Phase 2。更新 state.json：current_phase=2，files_created 追加 01-requirements.md。
