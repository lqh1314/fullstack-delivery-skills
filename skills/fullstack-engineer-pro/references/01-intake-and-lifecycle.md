# 01 · 任务分诊与全栈生命周期

> 对应主线 A。目标：把模糊任务变成可设计、可验证、可交付的流水线，且每一步都有落盘、有闸门。

## 1. Phase 0：启动与会话恢复
1. 查工作目录是否已有 `.fse-pro/state.json`：
   - `in_progress`：读出 feature / current_phase，问用户「续跑 / 重开（归档旧会话）」；
   - `complete`：问是否归档后开新任务；不存在则新建。
2. **自动探测技术栈，不直接问用户能自己查到的东西**：找 `pom.xml/build.gradle`、`requirements.txt/pyproject.toml`、`package.json`、`go.mod`、框架配置、迁移目录，判断 greenfield / brownfield 与前后端框架、数据库、测试框架、构建工具。
3. 初始化状态：
```json
{
  "feature": "任务描述",
  "status": "in_progress",
  "project_type": "greenfield|brownfield",
  "stack": {"frontend": "", "backend": "", "database": "", "test": "", "build": "", "infra": ""},
  "language": "java|python|js-ts|mixed",
  "complexity": "spike|bounded|architectural",
  "current_phase": 1,
  "completed_phases": [],
  "files_created": [],
  "started_at": "ISO", "last_updated": "ISO"
}
```
解析标志：`--no-frontend`、`--no-db`、`--simple`、`--complex`。未指定按探测到的影响面判定，在 A1 向用户确认。

## 2. 先定任务类型（说出你的判断）
- **Spike**：问"能不能做/这样行不行"，产出是结论不是保留代码；给试探计划→同意→最小代价验证→建议交付。
- **Bounded**：落在已有流程上的单点改动；关键问题问清后对话内给短设计，点头即做。
- **Architectural**：新项目/新子系统/改变他人依赖的接口或结构；走完整五阶段。
- 拿不准选更重；中途暴露隐藏复杂度立即停机升级，不允许悄悄降级。

## 3. A1 需求与业务（闸门 A）
**一次只问一个问题**，每题给 2–3 个建议选项 + "自己描述"，等回答再问下一个：
1. 问题与用户：解决谁的什么痛点？没有它现在怎么办？
2. 成功画面：做成后用户操作/结果具体变成什么样？
3. 验收标准：哪些可测条件满足才算 done（写成可勾选、可被测试验证）。
4. 范围边界：明确**不做**什么（比做什么更重要，防蔓延）。
5. 技术约束：既有接口约定、指定框架/数据库、延迟与兼容要求、复用的鉴权体系。
6. 依赖影响：上下游服务、数据迁移、受影响的既有功能。
7. 技术栈确认：把 Phase 0 探测结果给用户确认；brownfield 以探测为准。

前提可疑（为不存在的用户做复杂功能、与现有产品重复）要直接质疑并给替代思路，不照单全收。**没有可测验收标准不允许进入设计。**

`01-requirements.md` 模板：问题陈述 / 成功画面 / 验收标准(勾选) / In·Out Scope / 技术约束 / 技术栈 / 依赖与影响 / 复杂度与裁剪标志。

**闸门 A**：用一页内摘要（问题、验收、范围外、技术栈）请用户选「批准进设计 / 修改 / 暂停」，未明确批准不进 A2。

## 4. A2 设计（闸门 B）
> brownfield 先读现有模型、路由、目录约定，新设计必须与既有模式一致。

### 4.1 数据模型先行（六项，缺一不进下一步）
1. 实体关系与基数（1:1 / 1:N / N:N）；2. Schema（类型、约束、默认、可空、枚举）；3. 索引策略（每条索引对应真实查询，说明复合索引顺序）；4. 可回滚迁移（扩展-迁移-收缩、默认值回填、兼容旧数据）；5. 查询模式（先有读写路径再定结构）；6. DAO/Repository 方法签名与职责。
### 4.2 架构设计
- 后端：端点清单 + 请求/响应 schema + 错误码与状态码 + 版本策略；服务层职责边界；鉴权授权粒度；外部集成的超时与失败处理。
- 前端：页面/容器/展示组件层级；服务端状态 vs 本地状态；路由与守卫；取数、缓存、乐观更新、请求竞态与重试。
- 横切：异常→错误响应→前端错误态的全链路；输入校验/XSS/CSRF/越权/敏感数据；技术风险清单与缓解。

**闸门 B**：一页摘要展示核心表关系、接口清单（方法+路径+作用）、组件树、最高三个风险，请用户批准后才允许写实现代码。

## 5. A3 实现（顺序不可调换：DB → 后端 → 前端）
通用纪律：
- **先读后写**：找项目中最相似的现有实现，沿用框架用法、目录、命名、错误处理与日志风格；不擅自引入新依赖/新范式。
- **小步垂直切片**：每完成一个可运行单元立即最小验证（导入不报错、单测能跑、页面能渲染），不攒到最后一起调。优先"一个端到端薄片走通"再横向铺开，而不是先写完全部后端再碰前端。
- **改动留痕**：每层结束写实现摘要（新建/改了哪些文件、关键决策、遗留问题）。
- 报错立即转主线 B 根因调试，不带病推进。

Step 1 DB：正向+回滚迁移 → 实体/模型 → Repository 覆盖设计查询 → 约束与索引 → 本地验证迁移正反可用。
Step 2 后端（读需求/架构/DB 摘要）：接口与契约一致；业务在服务层、控制器只做协议转换；事务边界清晰；入口统一校验；鉴权接入；关键路径结构化日志（不泄密）；手动验证成功与失败响应。
Step 3 前端（读需求/架构/后端摘要，纯后端跳过并写明原因）：组件分层；数据流；loading/empty/error 三态；表单校验/提交态/防重复/错误回显；乐观更新与回滚；响应式与基础可访问性；真实跑通主路径。

## 6. A4 验证（闸门 C，三路并行）→ 见 `08-quality-gates.md`
测试套件（正常/边界/错误三类，新代码覆盖 80%+）、安全审计（OWASP）、性能审计（N+1/索引/分页/包体）同时推进、互不替代。Critical/High 当场修复并复验；每修一个 bug 先写复现它的失败测试再修，该测试永久保留为回归用例。汇报实际运行结果（非估计），Critical/High 未清零不给"批准"选项。

## 7. A5 交付
- 部署：CI/CD 质量门；迁移作为独立阶段（先迁移后发布）；必要时特性开关灰度；liveness/readiness；核心指标告警；**含数据库回滚顺序的 runbook**；沿用现有部署体系不擅自更换。
- 文档：接口请求/响应/错误码示例；schema 变更与迁移回滚说明；ADR；交接摘要（做了什么、怎么验、已知限制、backlog）。
- 完成前真实验证（顺序执行，不用"应该可以"替代）：干净环境装依赖→类型/lint/构建→全量测试→迁移正反演练→真实启动按验收标准走主流程→确认 Critical/High 清零→清调试残留。任一项失败，修复后**重跑全部验证**。
- state.json 置 complete，最终总结含：产物清单、各层实现摘要、验证方式与结果、已知限制、下一步（PR/部署/灰度）。

## 8. 落盘文件命名速查
`.fse-pro/`：`01-requirements.md`、`02-database.md`、`03-architecture.md`、`04-db-impl.md`、`05-backend-impl.md`、`06-frontend-impl.md`、`07-verification.md`、`08-deploy.md`、`09-handoff.md`、`state.json`。Bounded 任务可合并但保留需求确认与真实验证；`--no-*` 跳过层要在对应文件写明原因。
